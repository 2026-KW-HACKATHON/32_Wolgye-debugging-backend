# #9 배치 추천 규칙 확정 (명세 문서)

- 관련 이슈: #9 (현서 담당, 구현 전) · 브랜치: `docs/slot-recommendation-rules`
- 작업: 메인 세션. 규칙은 사용자가 2026-10-03에 정했다

## 사용자 결정
1. 추천은 **가장 이상적인 칸, 한 칸**으로 한다
2. 조건에 맞는 칸이 없으면 **추천하지 않는다**
3. 태그를 하나 추가한다 → 차가 있는 칸용 `OCCUPIED`. 원래 태그 셋(`RECOMMENDED`/`EMPTY`/`UNAVAILABLE`)으로는 차 있는 칸을 나타낼 수 없었다
4. 기존 명세 예시는 이해가 안 된다 → 다시 썼다

## 명세에 반영한 내용 (`docs/openapi-mock.yaml`)
- `GET /buildings/{building_id}/slots/recommendations` 설명
  - 빌라의 모든 칸을 P 번호 순으로 주고, 칸마다 태그를 하나 붙인다
  - 태그 4개: `UNAVAILABLE`(사용 중지·예약) / `OCCUPIED` / `RECOMMENDED`(최대 1개) / `EMPTY`(+`will_block`)
- 추천 조건 (결정 1의 막힘 규칙을 그대로 쓴다)
  1. 내가 막히지 않는다: 앞 칸이 비었거나, 앞 칸 차가 나보다 늦게 나가지 않는다
  2. 내가 아무도 막지 않는다: 뒤 칸이 비었거나, 뒤 칸 차가 나보다 일찍 나가지 않는다
- "가장 이상적인 칸" = 조건을 만족하는 칸 중 다음 순서로 고른다
  1. 가장 안쪽(앞 칸 사슬을 따라 출구까지 거치는 칸 수가 가장 많은) 칸
  2. 같으면 P 번호가 작은 칸
  - 사용자는 "가장 이상적인 칸"이라고만 했다. 안쪽 우선은 기존 명세·#9 이슈의 "안쪽 칸 우선"을 따른 것이고, 동점 처리는 응답이 매번 같게 하려고 정했다
- `SlotTag` enum에 `OCCUPIED`를 추가했다. `SlotRecommendation`의 `reason` / `will_block` / `unavailable_reason`에는 어떤 태그일 때 오는지 설명을 붙였다
- 열린 질문 표에 19번 "배치 추천 규칙"을 확정으로 추가했다

## 예시를 고친 이유
- 기존 예시: P7(1007)이 `RECOMMENDED`(빈 칸)인데 P8(1008)의 `will_block: [1007]`. 빈 칸은 막을 수 없어서 서로 맞지 않았다
- 라벨이 `P7 (안쪽)`이었다. `label`은 칸 이름이라 `P7`로 고쳤다
- 새 예시: 빌라 3의 배치도·관리인 칸 목록 예시와 같은 상태를 쓴다
  - 1001~1004, 1006은 차가 있다
  - 1005는 사용 중지
  - 1007(앞 칸 1008)과 1008은 비어 있다
- 결과
  - P7: 앞 칸이 비었고 뒤에서 막을 차가 없으며 안쪽이라 `RECOMMENDED`
  - P8: 조건은 맞지만 출구 쪽이라 `EMPTY`, `will_block: []`
