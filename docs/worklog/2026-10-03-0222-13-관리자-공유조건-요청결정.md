## 구현 내용
- `GET /admin/buildings/{building_id}/share-offers`: 이 빌라 칸의 공유 조건 id 순
- `POST /admin/buildings/{building_id}/share-offers`: 칸마다 하나씩, 다른 빌라·비활성 칸이 하나라도 있으면 400 + 전부 취소. 등록일 ~ 9999-12-31, host = 호출한 관리인
- `PATCH /admin/share-offers/{offer_id}`: 보낸 필드만 수정, 시간 순서 재검사, 기존 요청 `total_price` 유지
- `DELETE /admin/share-offers/{offer_id}`: 204, 딸린 요청 CASCADE
- `GET /admin/buildings/{building_id}/share-requests`: `status`·`q` 필터, 상태별 `counts`, 커서 페이지네이션
- `PATCH /admin/share-requests/{share_request_id}`: 404 → 403 → 409 `ALREADY_DECIDED` → (수락) 409 `GARAGE_TIME_CONFLICT` / 409 `INSUFFICIENT_TOKENS`(PENDING 유지). 수락 시 토큰 이동, 수락·거절 모두 `SHARE_RESULT` 알림, 한 트랜잭션

## 명세와 다르게·명세에 없어서 정한 것과 이유
- `counts`는 필터와 무관한 빌라 전체 기준: 탭 숫자로 쓰이는 값이라 봄
- `q`: 이름·닉네임·차량 번호(공백 무시) 부분 일치
- `limit` 지원: 명세 경로엔 cursor 만 있으나 결정 14·25 공통 규칙
- 거절 사유는 200자 자유 문자열(DB `String(200)`), 프리셋 강제 안 함
- 수락 알림 본문 `P1 · 10월 2일 10~12시` (명세에 거절 예시만 있음)
- PATCH 의 null 불가 필드 null, `weekdays: []` → 400 `INVALID_INPUT` (DB NOT NULL 위반 409 를 피함)
- 수락/거절 로직은 `admin_shares.decide`에 새로 구현: `share_requests.py`는 #12 소유이고 기존 `decide`엔 겹침 사전 확인·알림·명세 메시지가 없음
