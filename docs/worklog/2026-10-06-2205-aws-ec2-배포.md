# AWS EC2 배포 (ECR + RDS + GitHub Actions)

- 관련 이슈: 없음 (배포 인프라) · 브랜치: `ci/aws-deploy`
- 작업: 메인 세션, 2026-10-06 사용자 요청
- 결과 주소: `http://<EC2 Elastic IP>/` (도메인 구매 전이라 HTTP만. 아래 "HTTPS 전환" 참고)

## 목표
- `main`에 머지하고 CI가 통과하면 사람 손 없이 운영 서버까지 배포한다
- DB는 컨테이너가 아니라 RDS(PostgreSQL + PostGIS)를 쓴다
- 배포가 실패하면 이전 버전이 계속 돌아가게 한다

## 구성
```
GitHub (main push) ─ CI ✅ ─▶ Deploy 워크플로
   ├─ build-push : OIDC → AWS Role → ECR 로그인 → 이미지 빌드 → push :<커밋 sha>
   └─ deploy     : scp(compose · nginx · 스크립트) → ssh → deploy/deploy.sh <이미지:sha>
EC2 (Docker)  nginx :80 ──▶ api :8000 (127.0.0.1에만 노출)
                              └──▶ RDS PostgreSQL 16 (외부 접근 불가, EC2에서만)
```

### 로컬과 운영의 차이
| | 로컬 `docker-compose.yml` | 운영 `docker-compose.prod.yml` |
|---|---|---|
| DB | `db` 컨테이너 (postgis/postgis:16-3.4) | RDS |
| api | Dockerfile로 빌드, 소스 폴더를 `/app`에 연결, `--reload` | ECR 이미지를 그대로 실행 (코드가 이미지 안에 있음) |
| 앞단 | 없음 (`:8000` 직접) | nginx `:80` |
| 환경변수 | `backend/.env` | EC2의 `~/chagok/.env` |

### 파일
| 파일 | 역할 |
|---|---|
| `.github/workflows/deploy.yml` | CI 성공(`workflow_run`) 또는 수동 실행(`workflow_dispatch`) 때 빌드 → push → 배포 |
| `Dockerfile` | 운영 이미지. non-root(`app`) 실행, `HEALTHCHECK`, nginx 뒤에서 `--proxy-headers` |
| `.dockerignore` | `.env`, `tests/`, `.venv/` 등이 이미지에 들어가지 않게 한다 |
| `docker-compose.prod.yml` | 운영 compose (api + nginx, db 없음) |
| `deploy/nginx/conf.d/default.conf` | `:80` → `api:8000` 프록시 |
| `deploy/deploy.sh` | EC2에서 실행: ECR 로그인 → pull → `alembic upgrade head` → 재시작 → `/health` 확인 → 실패 시 롤백 |
| `deploy/compose.sh` | 지금 배포된 이미지로 `docker compose`를 실행하는 래퍼 (로그 보기, cron 등) |

### 배포 순서 (`deploy/deploy.sh`)
1. EC2 Instance Role로 ECR에 로그인한다 (EC2에 AWS 키를 두지 않는다)
2. 새 이미지를 pull한다
3. 새 이미지로 `alembic upgrade head`를 실행한다. **실패하면 여기서 멈추고**, 돌고 있던 컨테이너는 그대로 둔다
4. `up -d`로 api를 새 이미지로 바꾼다
5. `http://127.0.0.1:8000/health`를 30초 동안 확인한다
   - 성공: `~/chagok/.image.env`에 지금 이미지를 기록한다
   - 실패: 로그를 출력하고 `.image.env`에 있던 **이전 이미지로 되돌린 뒤** exit 1 → Actions job도 실패로 표시된다

> ⚠️ 롤백은 이미지만 되돌리고 **마이그레이션은 되돌리지 않는다.** 마이그레이션은 이전 코드와도 호환되게 작성한다. 예를 들어 컬럼을 지울 때는 "코드에서 사용 중단 → 배포 → 다음 배포에서 컬럼 삭제" 순서로 나눈다.

## 처음 한 번 하는 설정
리전은 시드니(`ap-southeast-2`)를 기준으로 적었다. **ECR · EC2 · RDS는 모두 같은 리전**에 만들고, GitHub 변수 `AWS_REGION`도 이 값과 같아야 한다 (한국 사용자가 많다면 서울 `ap-northeast-2`가 응답이 더 빠르다).

### 1. ECR
1. ECR → 리포지토리 생성: 이름 `chagok-api`, **프라이빗**
   - 이름은 GitHub 변수 `ECR_REPOSITORY`, 아래 권한 정책의 `Resource`와 **똑같아야** 한다. 다르면 push가 `The repository with name '...' does not exist`로 실패한다
   - "태그 변경 불가능(immutable)"은 켜도 된다. 워크플로가 커밋 sha 태그만 올리고 같은 태그를 덮어쓰지 않는다
2. 수명 주기 정책: "이미지 수 > 10이면 만료"로 오래된 이미지를 지운다

### 2. GitHub OIDC Role (Actions → ECR push)
1. IAM → 자격 증명 공급자 → OpenID Connect 추가
   - 공급자 URL `https://token.actions.githubusercontent.com`, 대상 `sts.amazonaws.com`
2. IAM → 역할 생성 → 웹 자격 증명 → 위 공급자. 만든 뒤 신뢰 정책을 아래처럼 바꾼다.
   - 워크플로가 `environment: production`을 쓰므로 `sub`는 `<접두어>:environment:production` 형식이다
   - **이 리포는 GitHub의 불변 식별자(immutable subject)를 쓴다.** 그래서 접두어가 `repo:<조직>/<리포>`가 아니라 조직 · 리포 이름 뒤에 숫자 ID가 붙은 형식이다. 접두어는 아래 명령으로 확인한다 (`sub_claim_prefix`)
     ```bash
     gh api repos/2026-KW-HACKATHON/32_Wolgye-debugging-backend/actions/oidc/customization/sub
     ```
   - 접두어가 틀리면 Actions의 `configure-aws-credentials` 단계가 `Not authorized to perform sts:AssumeRoleWithWebIdentity`로 실패한다
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Principal": { "Federated": "arn:aws:iam::<계정ID>:oidc-provider/token.actions.githubusercontent.com" },
       "Action": "sts:AssumeRoleWithWebIdentity",
       "Condition": {
         "StringEquals": {
           "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
           "token.actions.githubusercontent.com:sub": "repo:2026-KW-HACKATHON@329474081/32_Wolgye-debugging-backend@1384614669:environment:production"
         }
       }
     }]
   }
   ```
3. 권한 정책 (인라인): ECR push만 허용한다. `ecr:GetDownloadUrlForLayer`가 빠지면 push가 `not authorized to perform: ecr:GetDownloadUrlForLayer`로 실패한다 (이미 있는 레이어를 확인할 때 쓴다)
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       { "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*" },
       {
         "Effect": "Allow",
         "Action": [
           "ecr:BatchCheckLayerAvailability", "ecr:BatchGetImage", "ecr:GetDownloadUrlForLayer",
           "ecr:InitiateLayerUpload", "ecr:UploadLayerPart", "ecr:CompleteLayerUpload", "ecr:PutImage"
         ],
         "Resource": "arn:aws:ecr:ap-southeast-2:<계정ID>:repository/chagok-api"
       }
     ]
   }
   ```

### 3. EC2
1. 인스턴스 시작: Ubuntu Server 24.04 LTS (amd64), `t3.small` 권장 (`t3.micro`는 메모리 1GB라 빌드 없이 실행만 해도 빠듯하다). 볼륨은 gp3 15~20 GiB면 충분하다 (DB는 RDS라 EC2에는 OS · Docker 이미지 · 로그만 쌓인다). SSH 사용자 이름은 `ubuntu`다
2. 보안 그룹 `chagok-ec2-sg`: 인바운드 `80` 0.0.0.0/0, `22` 0.0.0.0/0
   - GitHub Actions 러너 IP는 고정되지 않아 22번을 좁힐 수 없다. 대신 SSH는 키 인증만 쓴다
3. IAM 역할(인스턴스 프로파일) 연결: `AmazonEC2ContainerRegistryReadOnly`
4. **Elastic IP**를 할당하고 연결한다 (붙이지 않으면 인스턴스를 재시작할 때마다 IP가 바뀐다)
5. 접속해서 Docker · compose · AWS CLI를 설치한다 (Ubuntu AMI에는 AWS CLI가 없다. `deploy.sh`가 ECR 로그인에 쓴다. cron은 이미 깔려 있다)
   ```bash
   ssh -i <키>.pem ubuntu@<Elastic IP>
   sudo apt-get update
   sudo apt-get install -y docker.io docker-compose-v2 curl unzip
   sudo systemctl enable --now docker
   sudo usermod -aG docker ubuntu          # 로그아웃 후 다시 접속해야 적용된다

   curl -fsSL "https://awscli.amazonaws.com/awscli-exe-linux-$(uname -m).zip" -o /tmp/awscliv2.zip
   unzip -q /tmp/awscliv2.zip -d /tmp && sudo /tmp/aws/install

   docker compose version && aws --version
   aws sts get-caller-identity             # Instance Role 이 붙었는지 확인 (ARN 이 나오면 성공)
   ```

### 4. RDS
1. RDS → 데이터베이스 생성: PostgreSQL 16, 템플릿 "프리 티어"(또는 `db.t4g.micro`), DB 이름 `chagok`
2. 연결: **퍼블릭 액세스 아니요**, EC2와 같은 VPC
3. 보안 그룹 `chagok-rds-sg`: 인바운드 `5432`, 소스 = `chagok-ec2-sg` (EC2에서만 접속 가능)
4. PostGIS · `btree_gist`는 RDS에서 지원된다. 마스터 사용자는 `rds_superuser`라서 `alembic/versions/0001`, `0002`의 `CREATE EXTENSION`이 첫 배포 때 그대로 실행된다. 따로 설치할 것은 없다.
5. **PostgreSQL 15 이상 RDS는 SSL 연결이 강제된다** (`rds.force_ssl=1`). 그래서 아래 `.env`의 URL에 SSL 옵션을 붙인다. 빠뜨리면 `no pg_hba.conf entry ... no encryption` 오류가 난다.

### 5. EC2의 운영 환경변수 `~/chagok/.env`
레포와 이미지에는 들어가지 않는다. EC2에서 직접 만든다.
```bash
mkdir -p ~/chagok && cd ~/chagok
openssl rand -hex 32      # SECRET_KEY 로 쓸 값
vi .env
chmod 600 .env
```
```ini
APP_NAME=chagok-chagok-api
ENV=prod
API_V1_PREFIX=/api/v1

DATABASE_URL=postgresql+asyncpg://<마스터유저>:<비밀번호>@<RDS 엔드포인트>:5432/chagok?ssl=require
DATABASE_URL_SYNC=postgresql+psycopg2://<마스터유저>:<비밀번호>@<RDS 엔드포인트>:5432/chagok?sslmode=require

SECRET_KEY=<openssl rand -hex 32 결과>

# FE 주소가 정해지면 넣는다 (JSON 배열)
CORS_ORIGINS=["http://localhost:5173"]
```
- 비밀번호에 `@ : / ?` 같은 문자가 있으면 URL 인코딩해야 한다. 처음부터 영문 · 숫자로만 만드는 편이 편하다.
- `.env`를 바꾼 뒤에는 `~/chagok/deploy/compose.sh up -d`로 api를 다시 만든다 (`restart`로는 환경변수가 다시 읽히지 않는다).

### 6. GitHub 설정
리포 Settings → Environments → `production` 생성 (필요하면 "Required reviewers"를 켜서 배포 전에 승인을 받게 할 수 있다)

| 종류 | 이름 | 값 |
|---|---|---|
| Variable | `AWS_REGION` | `ap-southeast-2` |
| Variable | `ECR_REPOSITORY` | `chagok-api` |
| Secret | `AWS_ROLE_ARN` | 2번에서 만든 Role의 ARN |
| Secret | `EC2_HOST` | Elastic IP |
| Secret | `EC2_USER` | `ubuntu` |
| Secret | `EC2_SSH_KEY` | EC2 키 페어 `.pem` 파일 내용 전체 |

## 나중에: HTTPS 전환 (도메인 구매 후)
HTTP로 운영하면 생기는 제약:
- FE가 HTTPS(Vercel · Netlify · GitHub Pages 등)로 배포되면 브라우저가 `http://` API 호출을 차단한다 (mixed content). 이 경우 HTTPS 전환이 필수다.
- 비밀번호와 JWT가 암호화되지 않은 채로 오간다.

전환 순서 (CI/CD 워크플로와 `deploy.sh`는 그대로 쓴다):
1. 도메인 A 레코드를 Elastic IP로 연결하고, 보안 그룹에서 `443`을 연다
2. 첫 인증서를 발급한다 (nginx를 잠깐 내리고 80번을 certbot이 쓴다)
   ```bash
   ./deploy/compose.sh stop nginx
   docker run --rm -p 80:80 -v chagok_letsencrypt:/etc/letsencrypt certbot/certbot \
     certonly --standalone -d <도메인> -m <이메일> --agree-tos -n
   ```
3. `docker-compose.prod.yml`: nginx에 `443:443`과 `chagok_letsencrypt` · webroot 볼륨을 추가하고, 12시간마다 `certbot renew --webroot`를 실행하는 `certbot` 서비스를 추가한다
4. `deploy/nginx/conf.d/default.conf`: `:80`은 `/.well-known/acme-challenge/`만 응답하고 나머지는 `301 https`로 보낸다. `:443 ssl`에서 `/etc/letsencrypt/live/<도메인>/` 인증서로 지금 프록시 설정을 그대로 쓴다
5. EC2 `.env`의 `CORS_ORIGINS`를 FE의 https 주소로 바꾼다
6. PR로 머지하면 자동 배포된다

## 검증한 것 (로컬)
- `docker build` 후 이미지 안에 `.env` · `tests/`가 없고, `app`(uid 1000)으로 실행되는 것을 확인했다
- EC2의 `~/chagok`과 같은 구조를 만들어 `deploy.sh`를 실행했다. ECR은 로컬 레지스트리(`registry:2`)로, `aws`는 가짜 스크립트로 대신했다
  - 첫 배포: 마이그레이션이 `0004`까지 적용되고, nginx를 거친 `/health` 200, `/docs` 200
  - 두 번째 배포: api 컨테이너가 바뀐 뒤에도 nginx가 새 컨테이너로 연결된다 (Docker DNS로 매번 다시 찾는다)
  - 기동 즉시 죽는 이미지 배포: 헬스체크 실패 → 이전 이미지로 롤백 → exit 1, `/health` 200 유지
  - `compose.sh run --rm api python -m app.jobs.block_alert` 실행 확인

## 첫 배포 (2026-10-06, AWS)
`main` 머지(#44) 후 Deploy 워크플로로 배포했다. 세 번 막혔고, 모두 AWS 설정 문제였다.

| 실패한 단계 | 오류 | 원인 → 조치 |
|---|---|---|
| `configure-aws-credentials` | `Not authorized to perform sts:AssumeRoleWithWebIdentity` | 신뢰 정책 `sub`가 불변 식별자 형식이 아니었다 → 위 2번의 `sub`로 수정 |
| `build-push` (push) | `not authorized to perform: ecr:GetDownloadUrlForLayer` | Role 권한 정책에 액션이 빠졌다 → 위 2번의 권한 정책으로 교체 |
| `build-push` (push) | `The repository with name 'chagok-api' does not exist` | ECR 리포지토리를 다른 이름(`chagok/backend`)으로 만들었다 → `chagok-api`를 새로 만듦 |

배포 후 외부에서 확인했다: `GET /health` 200, `GET /docs` 200, 없는 계정으로 `POST /api/v1/auth/login` → 401 `INVALID_CREDENTIALS` (RDS 조회까지 정상).
